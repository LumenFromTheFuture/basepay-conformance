1. **Budget**: spend cap per wallet/run/day (Cycles' lane)

=== arian-gogani (2026-06-24T21:31:24Z) ===
the 3-axis policy taxonomy (budget, contract-risk, counterparty-risk) with `Decision { signals: Record<string, any> }` is the right shape for the gate side. one architectural cut worth pinning so the broader picture is visible: the policy *decision* and the *evidence* of that decision are two separable concerns, and AgentKit will eventually need both.

right now `Decision` answers "should this wallet action proceed." in a regulated production deployment, the auditor will also ask "prove that the decision actually fired, with these signals, at this time, and the action that ran matched what was approved." that question is not answered by the live policy hook. it is answered by a signed record of the decision, plus a signed record of the outcome, joined by a content-derived identifier so a third party can verify the chain offline.

for AgentKit specifically, the natural shape:

1. `PolicyProvider` returns `Decision { allowed, signals, reason_codes }`. existing.
2. AgentKit emits a pre-execution receipt over the canonical decision payload (wallet, action_type, scope, policy_version, signals digest, timestamp_ms). signed with the agent's own Ed25519 key.
3. action executes (or does not).
4. AgentKit emits a post-execution receipt with the same identifier, capturing the outcome (executed transaction hash, failure reason, settlement result).

the join key is content-derived: `SHA-256(JCS({wallet, action_type, scope, policy_version, timestamp_ms}))`. recomputable by a verifier with only the receipt fields and the agent's published Ed25519 key, no AgentKit dependency. this is the property that makes the receipt useful as compliance evidence even when the audit is adversarial to the operator.

the receipt format itself is converging across the broader ecosystem. four independent implementations recently demonstrated byte-identical cross-implementation hashes against the same canonical-bytes discipline (RFC 8785 JCS): vaara, agent-guard, the x402 settlement-receipt extension, and nobulex. AgentKit choosing one of those as the reference implementation for the receipt side, while keeping `PolicyProvider` provider-agnostic, would give the gate-plus-evidence story without re-inventing the receipt format.

## Reference adapter (implements the RFC's `ActionPolicyProvider`)

Combines both: good reputation **and** a real economic footprint.

```ts
import { wrapFetchWithPayment, x402Client } from "@x402/fetch";
import { ExactEvmScheme } from "@x402/evm";
import { privateKeyToAccount } from "viem/accounts";

const REP = "43s9hQRurMGjuYnC1r2ZwS6xSQktbFyXMPMqGKUFJojb"; // Agent0 ERC-8004 — subjective
const PAY = "Cb56epg3EvQ6JRpPfknbkM54QxpzTvLa7mwKNQQfUyoj"; // x402 Base — objective payment history
const gw = (id: string) => `https://gateway.thegraph.com/api/x402/subgraphs/id/${id}`;
const Q_REP = `query($w:Bytes!){agents(where:{agentWallet:$w},first:1){totalFeedback feedback(where:{isRevoked:false},orderBy:createdAt,orderDirection:desc,first:50){value}}}`;
const Q_PAY = `query($w:Bytes!){x402AddressSummaries(where:{address:$w,role:RECIPIENT},first:1){totalPayments totalVolumeDecimal lastPaymentTimestamp}}`;

// One small Base wallet (USDC only) pays the $0.01-per-lookup. Gasless — EIP-3009, no approvals.
const acct = privateKeyToAccount(process.env.REP_LOOKUP_KEY as `0x${string}`);
const x402 = wrapFetchWithPayment(fetch, new x402Client().register("eip155:8453", new ExactEvmScheme(acct)));
const gql = async (id: string, query: string, w: string) =>
  (await (await x402(gw(id), { method: "POST", headers: { "content-type": "application/json" }, body: JSON.stringify({ query, variables: { w } }) })).json())?.data;

const MIN_SCORE = 60;
const cache = new Map<string, { ok: boolean; meta: Record<string, string>; exp: number }>();

export const graphReputationProvider /*: ActionPolicyProvider*/ = {
  async beforeAction(ctx: any) {
    const to = counterpartyOf(ctx.args)?.toLowerCase();   // recipient / spender of the action
    if (!to) return { decision: "allow" };                // nothing to score

    let hit = cache.get(to);
    if (!hit || hit.exp < Date.now()) {
      try {
        const [rep, pay] = await Promise.all([gql(REP, Q_REP, to), gql(PAY, Q_PAY, to)]);
        const vals = (rep?.agents?.[0]?.feedback ?? []).map((f: any) => +f.value).filter(Number.isFinite);
        const score = vals.length ? Math.round(vals.reduce((a: number, b: number) => a + b, 0) / vals.length) : 0; // tag-aware weighting > naive mean
        const sum = pay?.x402AddressSummaries?.[0];
        const settled = sum ? Number(sum.totalPayments) : 0;
        const ok = score >= MIN_SCORE && settled > 0;     // good rep AND a real footprint
        hit = { ok, exp: Date.now() + 5 * 60_000, meta: {
          source: "thegraph:agent0+x402",
          repScore: String(score),
          x402Payments: String(settled),
          x402Volume: sum?.totalVolumeDecimal ?? "0",
        } };
        cache.set(to, hit);
      } catch {
        // fail-open so a network blip doesn't brick the agent; flip to deny for high-value flows
        return { decision: "allow", metadata: { source: "thegraph", note: "lookup_failed_fail_open" } };
      }
    }
    return hit.ok
      ? { decision: "allow", metadata: hit.meta }
      : { decision: "deny", reason: `counterparty below policy (rep ${hit.meta.repScore}, x402 payments ${hit.meta.x402Payments})`, metadata: hit.meta };
  },

  // Optional: close the loop — write ERC-8004 feedback on the counterparty after a settled action,
  // so the same registry you read for risk gets richer every time an agent transacts.
  // async afterAction(ctx, result) { /* submit Feedback to the reputation registry */ },
};
```

Things that matter for the Deployment Profiles spec:

- **No oracle in the path** — both are stateless 402s against public subgraphs. Anyone can run the same queries, audit the inputs, or self-host the indexer. The signal is as decentralized as the registries it reads.
- **Two signals, provider combines them** — subjective reputation (who vouched) + objective footprint (what actually settled on-chain). Thresholds, tag-weighting, time-decay, allow/denylists, and how you weight the two are yours. Keep `metadata` rich (`repScore`, `x402Payments`, `x402Volume`, `subgraph`) for the audit trail the RFC wants.
- **Cost** — $0.01 per subgraph per lookup ($0.02 for both); the TTL cache makes it ~$0.02 per counterparty per window, not per action. Reputation/volume move slowly, so 5–60 min is plenty.
- **Fail mode** — fail-open by default; fail-closed for high-value flows. Make it a profile knob.
- **`afterAction` write path** — the registry is writable, so a settled action can emit feedback → the signal compounds.

  ```ts
  if (Date.now() > approvedDecision.expires_at_ms)       throw policy("policy_unverifiable");
  if (execHash !== approvedCtx.recipient_allocation_hash) throw policy("context_drift");

  // 3. Only then: allowance, encode, send
  const approveTx = await ensureAllowance(walletProvider, BATCH_PAY, total);
  const hash = await walletProvider.sendTransaction({ ... });
  ```

  The negative test surface from your acceptance shape maps to: `context_drift` (changed recipient, changed amount, changed ordering — all produce a different `execHash`), `unbound_execution` (missing `decision_ref`), `policy_unverifiable` (expired TTL). === osr21 (2026-06-28T03:37:30Z) ===
The three pre-spend checks are correct and the insertion point before `ensureAllowance` is right. One gap: `decision_ref` is checked for existence but not atomically consumed before the spend path. Two concurrent submissions presenting the same approved `decision_ref` both pass all three checks — `decision_ref` present, TTL valid, `execHash` matches — before either has entered the spend path. Both then call `ensureAllowance` + `sendTransaction`, producing a double-spend. The checks are necessary but not sufficient unless consumption is atomic with entry.

  The Arc gasrefuel route hit this directly. The pattern we use is a two-set approach before any async spend-path work:

  ```ts
  // Entry — mark in-flight before any async ops; blocks concurrent duplicates
  if (pendingDecisionRefs.has(decisionRef) || consumedDecisionRefs.has(decisionRef)) {
    throw policy("unbound_execution");
  }
  pendingDecisionRefs.add(decisionRef);

  try {
    // The three checks (unbound_execution, policy_unverifiable, context_drift)
    if (!approvedDecision.decision_ref)                     throw policy("unbound_execution");
    if (Date.now() > approvedDecision.expires_at_ms)        throw policy("policy_unverifiable");
    if (execHash !== approvedCtx.recipient_allocation_hash) throw policy("context_drift");

    // Permanently consume before the irreversible step — before ensureAllowance
    consumedDecisionRefs.add(decisionRef);

    // Only then: allowance → encode → send
    const approveTx = await ensureAllowance(walletProvider, BATCH_PAY, total);
    const hash = await walletProvider.sendTransaction({ ... });
  } catch (err) {
    // If definitively pre-spend (gas estimation failure, RPC timeout before any call):
    //   consumedDecisionRefs.delete(decisionRef) — safe to permit retry
    // If ambiguous (ensureAllowance succeeded, sendTransaction threw):
    //   keep in consumedDecisionRefs — allowance may have changed, second send is unsafe
  } finally {
    pendingDecisionRefs.delete(decisionRef); // always release in-flight lock
  }
  ```

  `pendingDecisionRefs` closes the concurrent-duplicate window before any async work. `consumedDecisionRefs` closes the replay window across request lifetimes. Both are checked together at entry — the two-set pattern is necessary because an in-flight lock released on error must not re-open the permanent consumption record.

  One corollary on the error branch: if `ensureAllowance` completes and `sendTransaction` throws, `consumedDecisionRefs` must be kept (do not delete on error). The allowance has already been modified. Whether the action is retryable is an implementation question, but the `decision_ref` is not reusable regardless — a second invocation with the same approved context would be executing against a different on-chain state.

## Thread summary + open items (33 comments)

Posting a structured summary so the design is readable as a single reference, and to surface the open items that still need resolution before a PR can land. Tagging participants at the bottom.

---

### What's agreed

**Interface shape (constructor-injected, fully opt-in)**

```ts
export interface ActionContext {
  action: string;
  to?: string;
  amount_usdc?: string;
  aggregate_usdc?: string;
  recipient_count?: number;
  recipient_allocation_hash?: string;
  per_recipient_max?: string;
  transfer_mechanism?: 'direct' | 'eip3009' | 'permit' | 'x402';
  creates_recurring_obligation?: boolean;
  creates_commitment?: boolean;
}

export interface PolicyDecision {
  allowed: boolean;
  reason_codes?: string[];
  signal_refs?: Record<string, string>;
  policy_version: string;
  action_context_hash: string;  // sha256(jcs(ActionContext)) — policy-independent
  decision_ref: string;          // sha256(jcs({ action_context_hash, policy_version, issued_at_ms, expires_at_ms }))
  issued_at_ms: number;          // generated once, stored, hashed from stored value
  expires_at_ms: number;         // generated once, stored, hashed from stored value
}

export interface PolicyProvider {
  evaluate(ctx: ActionContext): Promise<PolicyDecision>;
}

export interface BasePayConfig {
  relayUrl?: string;
  policyProvider?: PolicyProvider; // absent = current behavior unchanged
}
```

**`recipient_allocation_hash` (batch pay)**

Hash over the full sorted address+amount pair vector — not just count or aggregate. Catches address substitution, amount redistribution, and silent reordering:

```ts
function recipientAllocationHash(
  recipients: Array<{ address: string; amount: bigint }>
): string {
  const normalized = recipients
    .map(r => ({ to: r.address.toLowerCase(), amount_atomic: r.amount.toString() }))
    .sort((a, b) => a.to.localeCompare(b.to) || a.amount_atomic.localeCompare(b.amount_atomic));
  return sha256(jcs(normalized)); // RFC 8785 JCS + SHA-256
}
```

**Three pre-spend checks (all five actions, before `ensureAllowance`)**

```ts
if (!decision.decision_ref)                        throw policy('unbound_execution');
if (Date.now() > decision.expires_at_ms)            throw policy('policy_unverifiable');
if (execHash !== ctx.recipient_allocation_hash)     throw policy('context_drift'); // batch only
```

**Two-set `decision_ref` consumption (before any irreversible step)**

```ts
if (pending.has(ref) || consumed.has(ref)) throw policy('unbound_execution');
pending.add(ref);
try {
  consumed.add(ref);     // permanent — before ensureAllowance, not before sendTransaction
  // ... allowance -> encode -> send
} finally {
  pending.delete(ref);   // always release in-flight lock
  // consumed is kept even on error if allowance may have changed
}
```

**Receipt / outcome taxonomy**

- `receipt_outcome`: structured enum `executed | failed | denied | expired | context_drift` — separate from wallet/relay/chain error strings returned to the LLM.
- Bilateral receipts: `action_context_hash` joins the pre-execution policy decision to the post-execution outcome. No callback to agent runtime or policy provider required to verify.
- Signing scheme and receipt library are implementation choices — nobulex (`@nobulex/core`, Python `nobulex`) is a reference, not a requirement.

---

### Open items

**1. `basepay_subscribe` — decision scope**

For the four transactional actions, `decision_ref` governs a single atomic operation. For `basepay_subscribe` the `decision_ref` should scope to _creation of the subscription_, not to subsequent `charge()` calls. `charge()` is callable by anyone on-chain once the subscription exists; it is a separate authority plane that cannot be gated by the same `decision_ref`. This distinction needs to be explicit — otherwise an auditor cannot determine whether an allowed subscription-creation `decision_ref` was intended to cover all future charges.

Proposed resolution: `creates_recurring_obligation: true` flags this at evaluation time; `expires_at_ms` applies only to the creation call; post-creation charges are governed by on-chain subscription state, not the policy hook.

**2. Gasless relay (`basepay_send_usdc_gasless`) — nonce scope**

The two-set pattern prevents the _policy evaluation_ from being replayed at the AgentKit layer. The EIP-3009 nonce is the on-chain guard against relay replay: `USDC.authorizationState(from, nonce)` transitions to `Used` on the first successful `transferWithAuthorization`. But the relay is an off-chain HTTP endpoint — if it is called twice before the first tx confirms, both submissions enter the mempool and the second reverts on-chain. The two-set pattern does not close this window because the relay call is an async operation outside AgentKit's `consumed` set.

This is a relay-level concern (the BasePay relay already tracks in-flight nonces), but it is worth calling out explicitly so implementations using a different relay do not assume AgentKit's `consumed` set is the only guard.

**3. Distributed deployment**

`pendingDecisionRefs` and `consumedDecisionRefs` are in-process `Map`s — they do not protect against concurrent invocations across multiple agent nodes or process restarts. For multi-node deployments the consumption store needs to be atomic and durable (e.g. Redis `SET NX` or a DB unique constraint on `decision_ref`). The interface does not need to mandate this, but the reference implementation docs should note the assumption.

**4. Python implementation**

The original RFC checked both TypeScript and Python. The entire design thread has been TypeScript-only. The Python equivalents of `action_context_hash`, `decision_ref`, `recipientAllocationHash`, and the two-set pattern have not been addressed. The `nobulex` Python package exists (`pip install nobulex`), but the `PolicyProvider` protocol shape for Python has not been sketched since the original RFC post.

**5. PR status**

No PR has been opened against the policy hook scaffolding. Three people have offered to contribute:
- @amavashev — original RFC author, offered a Cycles adapter (last active Apr 22; the design has changed significantly since)
- @LumenFromTheFuture — said 'drafting PR logic' on Jun 27; no link posted
- @osr21 — confirmed the hook scaffolding is not yet in `lib/agentkit/src/basePayActionProvider.ts`

The hook scaffolding PR is separate from the BasePay action provider PR (#1333). #1333 adds the action provider without the hook; the hook PR adds the interfaces, wires `policyProvider` into `BasePayConfig`, and adds the five pre-spend check blocks to each action method.

**6. Conformance test surface**

The [argentum-core conformance fixture](https://github.com/giskard09/argentum-core/tree/main/examples/conformance/basepay) already covers `action_context_hash` / `action_ref` for the four BasePay actions (10/10 vectors passing). The new outcome taxonomy (`context_drift`, `unbound_execution`, `policy_unverifiable`, `policy_denied`, `unauditable_outcome`) is not yet represented in those vectors. Adding negative vectors for each failure mode would give the hook a cross-implementation test surface independent of any one AgentKit version — the same property that makes the existing `action_ref` vectors useful.

**7. Policy hook acceptance tests → test file**

@rpelevin's five acceptance tests are specified in prose but have not been mapped to a test file. The `basepayActionProvider.test.ts` pushed to PR #1333 today covers schema validation and action invocation paths. The policy hook tests (context_drift, policy_unverifiable, double-spend two-set) will need a separate test block once the hook scaffolding PR lands.

=== osr21 (2026-06-29T10:05:26Z) ===
@m13v — the gap you're describing is real and present in the current implementation, though it lands slightly differently from the `afterAction`/`onActionError` split in the original RFC.

The current `PolicyProvider` interface (PR #1349) has only `evaluate()` — no callbacks after execution. The equivalent mechanism is `receipt_outcome` as a structured field on the post-action record (agreed in comments #29–#30). But that field is only useful if the action code correctly maps on-chain outcome to it. Right now it doesn't: `waitForTransactionReceipt` is called on every action path, but `receipt.status` is never checked. A tx that gets included but reverts on-chain returns the same success string as one that settles. The `receipt_outcome` field would emit `executed` in both cases.

Viem's `waitForTransactionReceipt` returns `TransactionReceipt` which has `status: 'success' | 'reverted'`. The fix is to check it before returning:

```ts
const receipt = await walletProvider.waitForTransactionReceipt(hash);
if ((receipt as { status?: string }).status === 'reverted') {
  // receipt_outcome: 'failed' — budget reservation releases, not settles
  return `Error: transaction reverted on-chain.\nTransaction: ${txLink(hash)}`;
}
// receipt_outcome: 'executed' — budget settles
return `Sent ${args.amount} USDC to ${args.to}\nTransaction: ${txLink(hash)}`;
```

This maps your `afterAction` vs `onActionError` framing exactly onto the current design: `status === 'success'` is the `afterAction` path (settle); `status === 'reverted'` is the `onActionError` path (release). The difference from the original RFC is that the branch happens inside the action method rather than as a callback, but the budget provider's obligation is the same — it can trust `receipt_outcome` only if the action code made the distinction.

There's a second instance of the same gap on the gasless path that's worse: `sendUsdcGasless` returns success as soon as the relay responds with `{ txHash }` — there is no `waitForTransactionReceipt` call on the relay's tx hash at all. The relay HTTP 200 + on-chain revert is not detectable in the current implementation. For the gasless path, the fix is either to poll `waitForTransactionReceipt` on `data.txHash` before returning, or to document explicitly that gasless `receipt_outcome` is relay-confirmed, not on-chain-confirmed, and let the budget provider decide what settlement tier that represents.

Concretely, the `receipt_outcome` taxonomy from comments #29–#30 needs one clarification to be actionable:

- `executed` = `waitForTransactionReceipt` returned `status: 'success'` (on-chain confirmed, full amount settled)
- `failed` = `waitForTransactionReceipt` returned `status: 'reverted'` OR action threw before any wallet contact (budget releases in both cases)
- `relay_submitted` (new) = relay accepted the authorization but on-chain confirmation was not awaited (gasless path only; budget provider decides settlement policy)

Without that distinction, a budget provider receiving `executed` cannot tell whether the spend actually landed.

cc @LumenFromTheFuture — this is a concrete code change for PR #1349: check `receipt.status` on all four `waitForTransactionReceipt` call sites (L185, L352, L411, L475) and decide the gasless confirmation policy.

  The OWASP clarification surfaces something actually useful: the **bilateral receipt pattern** in ast09.md — admission receipt (what was authorized before dispatch) + outcome receipt (what actually happened), with a content-derived join key — maps directly onto the `decision_ref` + `receipt_outcome` design already agreed in this RFC (comments #29–#30 and the m13v exchange upthread). That convergence is worth naming, not because it makes any implementation normative, but because it gives the pattern an external reference point:

  - Admission receipt → `evaluate()` returning `{ allowed: true, decision_ref, ... }` before the action fires
  - Outcome receipt → `receipt_outcome: 'executed' | 'failed' | 'relay_submitted'` after the action completes (with the receipt.status check on all four `waitForTransactionReceipt` call sites, per the comment to @LumenFromTheFuture)
  - Content-derived join key → `action_context_hash = sha256(jcs(ActionContext))` — already the agreed binding between the two

  So the bilateral pattern in OWASP AST09 and the RFC's existing mechanism are convergent designs, not competing ones. Any `trust_signal_ref` implementation — Nobulex, ERC-8004 Validation Registry, or anything else — that produces an offline-verifiable (admission, outcome) pair keyed by `action_context_hash` satisfies both. That's the concrete spec guidance a receipt producer needs to be interoperable with this RFC's `CounterpartyContext`.
